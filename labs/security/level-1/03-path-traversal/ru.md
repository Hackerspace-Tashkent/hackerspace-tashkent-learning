# Практика: выйти за пределы своей папки

## Что дано

В `lab-work/` фикстура создала:

- `public/` — папка, файлы из которой **положено** отдавать:
  `index.html` и `notes.txt`;
- `secret.txt` — служебный файл **рядом** с `public/`, но не внутри.
  Наружу он уходить не должен.

## Порядок работы

1. Подготовь фикстуру:

```bash
bash setup.sh
```

2. Посмотри, что получилось:

```bash
ls -R lab-work
```

3. Напиши `srv.py`:

- маршрут `GET /` отдаёт `public/index.html`;
- маршрут `GET /<имя файла>` отдаёт файл из `public/` по имени из
  запроса;
- `python3 srv.py <порт> [--unsafe]` — порт аргументом, плюс
  необязательный флаг;
- **без флага** сервер работает безопасно и не выпускает наружу
  ничего, кроме файлов из `public/`;
- **с флагом `--unsafe`** он склеивает имя с `public/` без
  проверок — так дыра становится видна.

Склейка выглядит так:

```python
path = os.path.join(ROOT, name)
```

4. Запусти и убедись, что обычный файл отдаётся:

```bash
cd lab-work
python3 srv.py 8103
```

В другом терминале:

```bash
curl http://127.0.0.1:8103/notes.txt
```

5. Обойди сервер, запущенный **с флагом** `--unsafe`:

```bash
cd lab-work
python3 srv.py 8103 --unsafe
```

В другом терминале отправь:

```
curl --path-as-is http://127.0.0.1:8103/../secret.txt
```

Флаг `--path-as-is` нужен, чтобы `curl` не сократил путь сам. Если
ответ принёс содержимое `secret.txt` — дыра найдена.

6. **Не удаляй `secret.txt`.** Удалить файл — не решение, это проходит
проверку только потому, что файла нет. Проверка отдельно следит, чтобы
он остался на месте.

7. Теперь закрой дыру. Собери полный путь через `os.path.realpath` и
проверь, что он начинается с `public/`. Проверь оба варианта запроса:
`/../secret.txt` и `/../../etc/passwd`.

8. Перезапусти сервер и убедись: обычный файл по-прежнему отдаётся,
а обход больше не работает.

## Что проверяется

| | |
|---|---|
| 1 | файл `srv.py` существует |
| 2 | сервер отвечает по HTTP |
| 3 | обычный файл отдаётся |
| 4 | обход достаёт `secret.txt` |
| 5 | после защиты обход больше не работает |
| 6 | `secret.txt` не удалён, чтобы пройти проверку |

Обрати внимание на 5 и 6: сервер не может одновременно отдавать
файл наружу и не отдавать. Поэтому у него два режима, а проверка
поднимает его дважды: сначала с `--unsafe`, потом без флага.

## Ответ, к которому стоит прийти

Почему одной проверки «нет `..` в имени» мало:

- `....//` и `%2e%2e%2f` — это тот же `../`, просто иначе написанный;
- имя может начинаться с `/` и оказаться абсолютным путём;
- символическая ссылка внутри `public/` ведёт наружу сама по себе;
- регистр и кодировка тоже имеют значение.

Надёжность появляется там, где сервер вообще перестаёт доверять строке
из запроса.
