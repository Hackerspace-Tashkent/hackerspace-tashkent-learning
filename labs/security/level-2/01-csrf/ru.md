# Практика: чужая страница меняет твою почту

## Что дано

В `lab-work/` фикстура создала:

- `evil.html` — страница с формой, которая отправляет чужой POST на
  твой сервер;
- `state.txt` — текущее состояние: `email=you@example.com`.

## Порядок работы

1. Подготовь фикстуру:

```bash
bash setup.sh
```

2. Посмотри, что появилось:

```bash
ls lab-work
cat lab-work/evil.html
cat lab-work/state.txt
```

3. Напиши `srv.py`:

- `GET /set` **ставит cookie сессии**; без него сервер считает, что ты
  гость;
- `GET /form` отдаёт форму смены почты;
- `POST /action` принимает `email` и пишет его в `state.txt`;
- `python3 srv.py <порт> [--unsafe]` — порт и необязательный флаг.

Базовый сервер без защиты выглядит так:

```python
cookie = "sid=abc123"
if "sid=" in self.headers.get("Cookie", ""):
    email = form.get("email")
    open("state.txt", "w").write("email=" + email)
    self.reply("ok: changed")
```

4. Запусти **уязвимый** сервер:

```bash
cd lab-work
python3 srv.py 8111 --unsafe
```

5. Возьми сессию и попробуй вручную:

```bash
curl -c jar.txt http://127.0.0.1:8111/set
curl -b jar.txt http://127.0.0.1:8111/form
curl -b jar.txt -X POST --data-urlencode 'email=you@example.com' \
  http://127.0.0.1:8111/action
cat state.txt
```

6. Теперь главное — **запрос без всякой формы на твоей стороне**.
Отправь POST, приложив cookie, но не приложив ничего, что доказывает,
что это ты:

```bash
curl -b jar.txt -X POST --data-urlencode 'email=attacker@example.com' \
  http://127.0.0.1:8111/action
cat state.txt
```

Почта сменилась. Именно это и делает `evil.html`: браузер отправил бы
тот же запрос, приложив cookie сам.

7. Теперь закрой дыру. При `GET /form` генерируй случайный токен:

```python
token = secrets.token_urlsafe(16)
sessions[sid] = token          # запоминаем на сервере
```

и клади его в форму как `<input type="hidden" name="csrf" value="...">`.

При `POST /action` сверяй присланное значение с тем, что лежит в
сессии. Не совпало — отказ, и почта не меняется.

8. Перезапусти **без флага** и прогони обе попытки: без токена — отказ,
с токеном из формы — успех.

## Что проверяется

| | |
|---|---|
| 1 | файл `srv.py` существует |
| 2 | сервер отвечает по HTTP |
| 3 | сервер ставит cookie сессии |
| 4 | в уязвимом режиме форма идёт без токена |
| 5 | в уязвимом режиме чужой POST проходит |
| 6 | в безопасном режиме форма содержит токен |
| 7 | без токена действие отклоняется |
| 8 | с правильным токеном действие проходит |

## Ответ, к которому стоит прийти

Токен работает не потому, что «защищает от CSRF», а потому, что чужая
страница не может его прочитать. Отсюда важные следствия:

- значение должно быть непредсказуемым, а не «имя пользователя плюс
  соль» — иначе чужая страница его угадает;
- токен привязан к сессии: cookie из другой сессии не подойдёт;
- проверять надо всё, что меняет состояние: выход, смену почты,
  удаление;
- `SameSite` и проверка `Origin` — это второй слой, а не замена токену.
