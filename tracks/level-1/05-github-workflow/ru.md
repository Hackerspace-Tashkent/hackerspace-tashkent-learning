# Урок 5. Работа на GitHub

## Что этот урок даёт

В предыдущем уроке ты работал с git локально: сделал коммит, создал ветку,
сольял обратно. Эта история никуда не уходила — она жила в папке на твоей
машине.

GitHub добавляет три вещи, которых в git нет:

1. **общий доступ** — историю видят другие;
2. **обсуждения** — можно спросить и ответить рядом с кодом;
3. **проверки** — автоматический код может сказать «сломалось».

Без GitHub git остаётся личным журналом. С ним — способ работать вместе.

## Форк и клон: в чём разница

**Форк** — это копия чужого репозитория у тебя в аккаунте на GitHub. Ты её
получил одной кнопкой, код никуда не копировался физически — это запись на
сервере GitHub.

**Клон** — это копия у тебя на машине, скачанная через `git clone`.

Порядок всегда такой:

```
чужой репозиторий  →  форк у тебя  →  клон на машину
```

Клонировать можно и сразу оригинал, но тогда ты не сможешь запушить: у тебя
нет прав на чужой репозиторий. Форк нужен именно для этого.

```bash
git clone https://github.com/твой-логин/hackerspace-tashkent-learning.git
```

Смотри, что в адресе — **твой логин**, а не `Hackerspace-Tashkent`. Если в
`git remote -v` оригинал — форк ты не сделал или склонировал не то.

## remote: куда идёт push

```bash
git remote -v
origin  https://github.com/твой-логин/... (fetch)
origin  https://github.com/твой-логин/... (push)
```

`remote` — это просто имя для адреса. Имён может быть сколько угодно:

```bash
git remote add upstream https://github.com/Hackerspace-Tashkent/hackerspace-tashkent-learning.git
```

`origin` — твой форк, куда ты пушишь. `upstream` — оригинал, откуда берутся
чужие изменения. В `push` ты используешь `origin`:

```bash
git push origin my-branch
```

## Ветка и синхронизация с оригиналом

Работаешь ты всегда в ветке, `main` не трогаешь:

```bash
git switch -c add-my-note
```

Пока оригинал живёт своей жизнью, твой форк отстаёт. Забрать изменения:

```bash
git fetch upstream
git switch main
git merge upstream/main
git switch add-my-note
git merge main
```

Последние две команды вливают `main` в твою ветку, чтобы они не разошлись.
Если при этом твоя ветка что-то меняла в тех же строках — Git покажет конфликт.
Это не поломка, это запрос решить руками, что остаётся.

## Pull request

**Pull request (PR)** — предложение «вот мои изменения, посмотри и влей».

Формально PR — не «запрос на слияние», а **просьба о ревью**. Слияние может
и не произойти: человек может попросить переделать. Поэтому описание PR важнее
самой кнопки Merge.

Описание — это обращение к человеку. Минимум:

```markdown
## Что изменено
## Как проверить
## Что я проверил сам
```

Третий пункт необязателен по формату, но ценнее остальных. Он показывает,
что автор не просто нажал кнопку.

Через браузер: push → GitHub покажет кнопку Compare & pull request.
Через терминал, если есть `gh`:

```bash
gh pr create --fill
gh pr status
```

## Issue: разговор без кода

Issue — это заявка, вопрос или идея. Кода может не быть вовсе.

Issue и PR — разные вещи, хотя оба живут на GitHub:

| | Issue | Pull request |
|---|---|---|
| Про что | вопрос, идея, баг | конкретные изменения в коде |
| Есть код | не обязательно | обязательно |
| Кто закрывает | автор или мейнтейнер | мейнтейнер после ревью |

Ошибку без готового исправления описывают в issue. Готовое исправление — в PR,
и в описании ссылаются на issue, где обсуждалось.

Правило хорошего issue: что ожидалось, что получилось, как воспроизвести.

## Ревью

Ревью — чтение чужого изменения с ответом. Это не поиск ошибок в стиле,
это проверка «правильно ли сделано».

Полезное ревью отвечает на три вопроса:

- **понятно ли, что изменилось и зачем** (по описанию, а не по коду);
- **верно ли это работает** (есть ли способ проверить);
- **что здесь не учтено** (что сломается у других).

Фразы, которые не помогают: «исправь», «плохо», «не согласен». Помогают:
«вот этот случай падает, потому что…», «здесь не обработано пустое значение,
вот пример».

Мы не требуем формальных правил. Требуем одного: **комментарий должен
объяснять, что не так и как лучше.** Если человек не согласен — это нормально,
если он написал почему.

## Про настройки

Две вещи стоит настроить сразу, иначе удивишься позже:

```bash
git config --global user.name "Твоё Имя"
git config --global user.email "твоя@почта"
```

Без этого коммиты будут подписаны как `root` или вообще откажутся создаваться в
Codespaces.

Второе — `.gitignore`. В `.gitignore` попадает всё, что не должно в историю:
`lab-work/`, ключи, `.env`, временные файлы. Это уже настроено в нашем
репозитории, но в своём форке проверь, что список подходит.

## Что проверить самому

- [ ] `git remote -v` показывает твой форк, а не оригинал
- [ ] ветка называется не `main`
- [ ] в описании PR есть «что изменено» и «как проверить»
- [ ] `git status` чист перед коммитом

## Честно о том, что мы не проверяем

Практика не решает, твой PR хороший или нет. Его читает человек, и человек же
решает. Всё, что автоматически, — это про то, что файлы на месте и сданы в
правильном виде.
