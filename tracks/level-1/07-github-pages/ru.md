# Урок 7. GitHub Pages

## Что это такое

GitHub Pages — это бесплатный хостинг статических сайтов прямо из репозитория.
Ты кладёшь файл `index.html` в корень, включаешь Pages в настройках, и через
минуту сайт открыт по адресу.

```
репозиторий  →  включаешь Pages  →  GitHub собирает  →  сайт работает
```

Наш сайт как раз так и сделан: `https://hackerspace-tashkent.github.io/Hackerspace-Tashkent-website/`.

## Главное ограничение

Pages отдаёт **только статические файлы**. То есть `.html`, `.css`, `.js`,
картинки, шрифты.

Чего он **не умеет**:
- выполнять код на сервере — ни PHP, ни Python, ни Node;
- хранить базу данных;
- принимать формы, если нет внешнего сервиса;
- прятать секреты — всё, что в репозитории, видно всем.

Отсюда правило: **серверная логика — это VPS, статика — это Pages.** Если
сайту нужна база, у него два варианта: внешний сервис (Supabase, Airtable) или
свой сервер. Скрыть ключ API в Pages невозможно в принципе, секрет всегда виден
в коде страницы.

## Способ первый: из ветки

Проще всего и чаще всего достаточно.

1. Файл `index.html` лежит в корне `main`.
2. **Settings → Pages → Source: Deploy from a branch**, ветка `main`, папка
   `/ (root)`.
3. Сохранить. Через минуту-три сайт отвечает.

Важные детали, на которых спотыкаются:
- файл должен называться **именно `index.html`** (не `index.htm`, не `Index.html`);
- если сайт в подпапке, в адресе будет `/имя-папки/`;
- главная страница — это `index.html`, всё остальное доступно по именам файлов.

## Способ второй: через Actions

Нужен, если сайт собирается: генератор статических сайтов, шаблоны, обработка
изображений.

```yaml
name: Опубликовать сайт

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: '.'
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

Что здесь важно и обычно не очевидно:

**`permissions:`** — Actions по умолчанию не может публиковать страницы. Без
этих трёх строк деплой падает с ошибкой про права.

**Два job'а, а не один.** Сборка и публикация разделены: пересборка не должна
ломать уже работающий сайт. `needs: build` говорит «ждать первый».

**`environment: github-pages`** — специальное окружение, которое GitHub
создаёт сам. Именно оно привязывает деплой к Pages.

**Артефакт** — промежуточный результат сборки. `upload-pages-artifact`
упаковывает папку, `deploy-pages` её распаковывает и выкладывает.

## Свой домен

В **Settings → Pages → Custom domain** вписывается домен, затем в настройках
домена создаётся CNAME на `USER.github.io`.

Два предупреждения:
- домен начинает работать не сразу, проверка занимает от нескольких минут до
  суток, иногда дольше;
- если DNS не настроен, сайт будет висеть в статусе `DNS Check in Progress`
  и не откроется. Проверяй, что домен вообще резолвится, до того как ждать
  остальное.

Мы на этом споткнулись: `hackerspace.uz` не был настроен и не открывается. Рабочий
адрес — на Pages.

## Локальная проверка до публикации

Публиковать и смотреть результат — плохой цикл. Проверяй локально:

```bash
cd lab-work
python3 -m http.server 8000
```

Открой `http://127.0.0.1:8000` в браузере. Если локально работает, а на Pages
нет — дело в настройке Pages, а не в коде.

Так же работает Codespaces: там у порта есть кнопка «Open in Browser».

## HTTPS

Pages выдаёт сертификат автоматически. Принудительный HTTPS включается
переключателем в настройках. Своим доменом можно включить «Enforce HTTPS», но
сначала убедись, что домен открывается — иначе получишь сайт, недоступный
никому.
