# Когда shell исполняет то, что прислал пользователь

## Зачем это знать

В предыдущих темах вред приходил через SQL и через HTML: данные
превращались в запрос или в страницу. Здесь всё идёт до shell.

Сервер хочет «проверить, отвечает ли хост». Он пишет команду и запускает
её. Если имя хоста пришло из запроса и попало в строку команды как есть —
пользователь может дописать к ней своё.

Это **command injection**, внедрение команд.

## Где возникает

Опасная строка выглядит обычно и не вызывает подозрений:

```python
out = subprocess.run(
    f"ping -c 1 {host}",
    shell=True, capture_output=True, text=True)
```

`host` — из запроса. `shell=True` отдаёт строку интерпретатору, и тот
разбирает её на части. `;` в имени хоста превращает проверку в две
команды.

## Почему это не «редкий случай»

Проверка «а нет ли тут `;` или `&&`» не работает. Список запрещённых
символов всегда короче reality:

- разделители не только `;` — ещё `&&`, `||`, перевод строки, `$( )`;
- пробел позволяет передать аргументы, которых не было;
- обратные кавычки и `$()` работают без `;` вообще;
- URL-кодирование и обходы на уровне библиотеки добавляют новые пути.

## Что делать вместо этого

**Не создавать строку команды.** Передавать аргументы списком:

```python
out = subprocess.run(["ping", "-c", "1", host],
                     capture_output=True, text=True)
```

Здесь `host` — это один аргумент, а не текст программы. Даже если он
содержит `; cat flag.txt`, запустится `ping` с таким именем хоста и
больше ничего.

**`shell=False` по умолчанию.** Явный `shell=True` должен быть редкостью
и вызывать вопрос «почему здесь нельзя без него».

**Белый список, если без shell никак.** Не проверять строку на
отсутствие плохого, а проверять, что она входит в список разрешённых.

## Что ты сделаешь

Сервер сначала будет уязвимым. Ты внедришь команду, потом закроешь
дыру и объяснишь, почему проверка на символы хуже списка аргументов.

## Граница

Только свой компьютер, только `localhost`, только файлы фикстуры.
